# Task 4 实施报告：统一模拟支付和超时状态机

## 交付结果

- 新增统一 `PaymentGateway` 边界和默认 `MockPaymentGateway`，支付创建返回 `PROCESSING`，由服务端定时查询渠道终态。
- 新增用户支付创建与可信状态查询接口：
  - `POST /user/orders/{id}/payments`，要求 `Idempotency-Key` 请求头。
  - `GET /user/payments/{paymentNo}`，按当前登录用户校验支付单归属。
- 模拟支付成功在同一数据库事务内完成用户账户扣款、平台待结算账户入账、一笔资金转移、两条账本分录、支付单成功、订单转待接单和时间轴事件。
- 余额不足时支付单进入 `FAILED/INSUFFICIENT_BALANCE`，不产生资金转移或账本分录。
- 支付超时先将支付单置为 `CLOSED`，再条件取消待付款订单；调度顺序固定为先处理超时、后查询仍在处理中的渠道结果。
- 原有模拟支付入口已委托到新支付应用服务，不能绕过模拟余额和双向账本。
- 模拟渠道交易号可从数据库持久化值恢复，应用重启后仍可继续查询；业务层只依赖统一渠道模型，为后续微信 H5 支付适配器保留替换边界。

## 并发与幂等

- 客户端幂等键按 `userId:orderId:key` 作用域持久化，避免不同用户或订单互相碰撞。
- 支付单、订单和账户均使用数据库行锁与条件状态更新；重复成功结果最多产生一次扣款。
- 数据库生成列唯一约束保证同一订单最多一笔成功支付。
- 用户取消待付款订单时先锁定订单行，再检查处理中支付，消除取消和支付创建之间的检查窗口。
- 成功结算与超时关闭竞争时只有一个终态；`CLOSED` 支付单不能被迟到成功重新结算。
- 批量对账逐支付单隔离异常，单笔渠道查询失败不会中断整批任务。

## 数据库变更

- 新增迁移 `V20260920_01__add_payment_gateway_identity.sql`。
- `payment_transaction` 新增唯一渠道交易号 `gateway_trade_no` 和唯一回调事件号 `callback_event_id`，用于渠道追踪和第二层幂等保护。

## 已知边界

- 本任务实现的是可供普通用户使用的真实账本驱动模拟支付，不连接外部清算网络。
- 微信 H5 支付尚未实现；后续通过新增条件化 `PaymentGateway` 实现切换，用户浏览器端不应直接决定支付终态。
- 当前 `gateway.close()` 在数据库事务内执行；模拟渠道无网络副作用。接入真实微信前，应将外部关单调用改造成可重试的任务/补偿流程，避免长事务。
- 迁移已在 H2 MySQL 兼容模式验证，尚未在独立真实 MySQL 实例执行。
- 测试日志中的 Redis 未启动、Mockito 动态代理及既有编译器警告为非阻断环境警告。
