# 饱饱助手个性化健康饮食推荐实施报告

## 1. 实施结果

已按照《饱饱助手个性化健康饮食推荐实施计划书》完成首版工程能力建设，推荐决策由自由文本推测调整为“结构化事实、硬约束过滤、版本化规则和可解释排序”。

已完成模块：

1. 推荐契约、安全边界、风险等级、原因码和单位冻结；
2. 食材、营养、过敏原、套餐快照、时令规则数据底座；
3. 用户长期饮食档案、同意、删除和审计；
4. 类型化规则集校验、发布、下线、回滚和审计；
5. 实时候选、过敏与忌口过滤、营养目标评分和推荐轨迹；
6. Agent 意图、风险分级、受控槽位和 Java 推荐工具；
7. 用户端饮食档案与解释型推荐卡片；
8. 管理端营养、食材、过敏原和规则管理页面；
9. 质量看板、灰度开关、Prometheus 指标和 CI 门禁；
10. Flyway 迁移验证、API 冒烟测试和全量自动化回归。

## 2. 关键实现

### 2.1 安全裁决

- 过敏原状态为 `CONTAINS`、`MAY_CONTAIN`、`CROSS_CONTACT_RISK` 或 `UNKNOWN` 时不能通过对应过敏筛选；
- 没有过敏原声明等价于未知，不等价于安全；
- 忌口食材命中时直接排除；
- 复杂疾病和急性高风险请求不进入个性化推荐；
- 常见慢病场景没有已发布规则时返回 `RULES_UNAVAILABLE`；
- LLM 只能解释 Java 返回的推荐结果，不能补充额外菜品、营养或健康功效。

### 2.2 数据版本

- 菜品配方和营养档案采用独立版本；
- 只有 `VERIFIED` 且当前有效的营养版本参与推荐；
- 套餐只有在全部组成菜品完成审核后才能生成营养快照；
- 推荐请求保存当时的规则和数据版本；
- 规则集支持 `DRAFT → VALIDATED → PUBLISHED → OFFLINE/SUPERSEDED`。

### 2.3 用户控制

- 用户可以不创建长期档案，继续使用普通点餐；
- 档案支持地区、饮食方式、过敏、忌口和健康目标；
- 用户可随时删除长期档案；
- 推荐请求可以选择是否使用长期档案；
- 日志和推荐轨迹不保存模型思维过程。

用户端：

```text

POST /user/diet/recommendations
POST /user/diet/recommendations/{id}/feedback
```

管理端：

```text
GET/PUT /admin/diet/dishes/{dishId}/nutrition
POST /admin/diet/dishes/{dishId}/nutrition/{version}/verify
POST /admin/diet/setmeals/{setmealId}/nutrition/recalculate
GET/POST /admin/diet/rule-sets
POST /admin/diet/rule-sets/{id}/validate|publish|offline|rollback
GET /admin/diet/quality-dashboard
```

Agent 工具：

```text
get_diet_profile
recommend_personalized_meals
```

## 4. 配置与灰度

```text
DIET_RECOMMENDATION_ENABLED=true
DIET_PROFILE_ENABLED=true
DIET_MEDICAL_SCENARIOS_ENABLED=true
```

三个能力可独立关闭，关闭后不影响原有菜单搜索、购物车和订单链路。

## 6. 当前内容状态与上线限制

当前数据库已有 24 道菜，但没有可信的标准份量、完整配方和供应商营养标签，因此未自动生成或伪造营养值。目前质量看板会如实显示：

- 总菜品：24；
- 已审核营养菜品：0；
- 开发模拟营养菜品：24；
- 已发布食养规则：0。

开发环境已经可以使用显式标记为 `SIMULATED` 的一人份估算数据完成普通健康目标推荐；生产环境仍会忽略这些数据。慢病场景会在规则未发布时返回规则不可用，直到完成专业复核。

已经生成内容包：24 道菜的数据质量清单、45 条菜单明确食材记录、15 条可证明的过敏原 `CONTAINS` 声明、24 道菜一人份模拟营养、216 条模拟过敏原声明、17 条套餐组成及4个模拟套餐营养快照、4 个结构化规则草稿，以及 8 份带权威来源链接的知识库文档。包装商品标签未知的过敏原继续按 `UNKNOWN` 处理；其余 `FREE` 仅表示模拟配方范围内未加入，不代表真实门店无交叉接触。

正式开放前必须完成：

1. 获取真实配方、标准份量和营养来源；
2. 完成全部目标菜品的过敏原声明；
3. 由具备相应知识的人审核营养版本；
4. 根据权威指南制定并审核规则；
5. 对现有 219 条结构化评测用例完成人工复核，并持续补充真实失败样本；
6. 过敏与医生明确禁忌违规率达到 0 后再灰度开放。

## 7. 结论

首版技术平台已经具备安全承载个性化饮食推荐的能力，并能明确拒绝缺少数据或超出医疗边界的请求。剩余工作不应通过继续修改提示词解决，而是内容治理工作：真实配方、营养数据、过敏原声明、权威规则和专业审核。
