# 阶段一实施报告：账号、模拟支付基础与测试底座

## 一、实施结论

阶段一已完成，用户端已具备可持续扩展的正式账号、生产级模拟资金与支付链路，并建立 Chromium、WebKit 两种手机浏览器内核的端到端验收底座。

本阶段交付覆盖：手机号账号注册与登录、刷新会话、模拟账户和双向账本、用户可见钱包、模拟金领取、支付创建与可信状态查询、支付幂等和失败恢复、移动端核心流程自动化测试。前端不再根据 URL 参数判断支付成功，所有支付结果均以服务端支付单为准。

## 二、核心交付

### 2.1 正式账号体系

- 支持手机号、短信验证码、自设密码注册，以及手机号密码登录。
- Access Token 仅保存在页面内存；Refresh Token 使用 HttpOnly Cookie。
- 支持并发 401 单次刷新、请求重放、当前设备退出和全部设备退出。
- 注册、登录、刷新、退出均记录必要的安全审计；登录失败具备频率与锁定保护。

### 2.2 模拟资金与账本

- 注册时自动创建用户模拟账户并发放初始模拟金。
- 普通用户可查看可用余额、冻结金额和资金流水，并可主动领取模拟金。
- 每笔资金转移生成双向账本分录，余额更新采用版本控制，业务键和幂等键阻止重复入账或扣款。
- 管理端调账保留操作人、原因、调整前后余额等审计字段。

### 2.3 生产级模拟支付

- 支付网关通过统一接口隔离，目前使用可延迟完成、可恢复查询的模拟渠道。
- 创建支付单、渠道受理、轮询对账、账本扣款、订单更新、时间轴记录在服务端闭环完成。
- 同一订单的成功支付受数据库唯一约束保护；响应丢失或重复请求不会重复扣款。
- 用户端按 1、2、3、5 秒退避查询支付结果，最长等待 30 秒；支持查询失败重试、余额不足引导和支付恢复。
- 前端仅依赖统一的支付创建与查询接口，后续接入微信 H5 时可替换支付网关实现，不需要重写订单和钱包主流程。

### 2.4 移动端自动化测试底座

- Playwright 建立 `mobile-chrome` 与 `mobile-webkit` 两个项目，分别模拟 Android Chrome 和 iPhone WebKit。
- 自动化场景真实执行：注册、领取模拟金、新增默认地址、加入购物车、提交订单、支付、重放支付请求、核对钱包余额与唯一支出流水。
- E2E 使用独立 MySQL 和 Redis 临时容器、专用后端与 Vite 端口，不连接或修改开发数据库。
- 启动脚本在 `finally` 中清理本次创建的服务进程和容器；失败时保留日志用于诊断。
- Vite 代理支持通过 `USER_API_TARGET` 指定后端，默认开发配置保持不变。

## 四、运行方式

首次运行需要安装项目锁定版本的浏览器：

```powershell
Set-Location frontend/project-sky-user-web
npx playwright install chromium webkit
```

在仓库根目录执行全部移动端项目：

```powershell
.\scripts\run-user-e2e.ps1
```

也可以单独执行：

```powershell
.\scripts\run-user-e2e.ps1 -Project mobile-chrome
.\scripts\run-user-e2e.ps1 -Project mobile-webkit
```

脚本要求本机具备 Java 21、Maven、Node.js、npm 和 Docker；专用端口为 MySQL `13316`、Redis `16380`、后端 `18080`、前端 `15173`。

## 五、边界与后续阶段

- 本阶段只建立账号、支付和核心自动化底座；结算试算、配送时间与范围的完整校验属于阶段二。
- 订单时间轴的基础表和支付事件已落地，面向用户的完整时间轴、取消退款、售后与全局通知属于阶段三。
- 地址选择器、跨分类搜索、个人资料编辑，以及商品单页无限滚动属于阶段四。
- 当前开发与自动化环境在未配置百度地图 AK 时跳过真实距离调用；联调和生产环境再启用百度地图。
- 当前使用模拟支付网关；接入微信 H5 时需补充商户配置、下单参数、异步回调验签、主动查单和退款实现，并继续复用现有支付单、幂等与账本模型。
