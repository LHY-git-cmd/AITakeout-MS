# 用户端传统业务全链路优化设计说明

## 1. 文档信息

- 文档版本：1.0
- 设计日期：2026-09-18
- 适用项目：苍穹外卖用户端 Web、Spring Boot 服务端
- 目标终端：普通手机浏览器
- 当前支付渠道：生产级模拟支付
- 未来支付渠道：微信 H5 支付

## 2. 建设目标

本项目完善用户从注册登录、点餐、结算、下单、支付、订单查询、取消订单到金额返还的传统业务闭环，并覆盖交易过程中可能出现的价格变化、门店打烊、地址超范围、网络中断、重复操作、支付超时、回调丢失、退款失败和通知离线等异常情况。

本次建设范围包括：

1. 正式手机号账号体系和个人资料管理。
2. 跨分类商品搜索与单页无限滚动。
3. 地址三级联动、地理编码和配送范围预检。
4. 结算试算、预约配送、距离分段配送费和订单提交。
5. 生产级模拟账户、支付、退款和资金流水。
6. 订单状态机、订单时间轴、取消申请和售后处理。
7. 持久化通知中心和 WebSocket 实时提醒。
8. 后端、数据库、支付/地图契约和浏览器端到端自动化测试。

以下内容不在本次范围：

- 真实微信资金扣款与退款。
- 微信内置浏览器 JSAPI 支付。
- 地图拖拽选点和自动定位。
- 单个商品退款、部分金额退款和商家提现。
- 浏览器系统级 Web Push。
- Elasticsearch、拼音搜索和智能推荐。

## 3. 已确认的产品规则

### 3.1 支付与模拟账户

- 普通用户可见“模拟支付账户”、余额和资金流水。
- 页面明确标注模拟资金仅用于功能演示，不代表真实资金且不可提现。
- 新用户初始模拟余额为 500 元。
- 用户每次可领取 500 元模拟金，账户余额上限为 10000 元。
- 领取模拟金和管理端调账都必须生成资金流水。
- 管理端调账必须记录操作人、原因、调整前金额和调整后金额。
- 支付页面展示支付前余额、订单金额和预计支付后余额。
- 切换到真实微信支付渠道后，隐藏模拟余额和领取入口。

### 3.2 支付时限

- 待支付订单有效期为 15 分钟。
- 倒计时由服务端时间和订单过期时间计算。
- 剩余 2 分钟时给予一次明确提醒。
- 超时任务先关闭支付单，再取消订单。
- 超时取消后不自动恢复购物车，订单页提供“再来一单”。

### 3.3 取消和售后

- 待付款：用户可直接取消，不产生退款。
- 已支付且待接单：用户可直接取消，自动全额退款。
- 商家拒单或商家取消：自动全额退款。
- 制作中：用户提交取消申请，商家审批；批准后全额退款。
- 配送中：用户提交售后申请，商家审批。
- 已完成：送达后 24 小时内可提交整单售后申请。
- 第一版只支持整单全额退款。
- 同一订单最多存在一个进行中的取消或售后申请。
- 商家拒绝申请时必须填写原因。

### 3.4 配送

- 本地开发和自动化测试使用模拟地图服务。
- 联调、预发布和生产环境使用百度地图服务。
- 配送校验在所有环境中始终执行，禁止因未配置地图服务而跳过。
- 默认配送费：3 公里以内 5 元，3 至 5 公里 8 元，超过 5 公里不可配送。
- 距离区间、费用和最大配送距离全部配置化。
- 支持立即配送和预约配送。

### 3.5 搜索与通知

- 搜索菜品和套餐，覆盖名称、描述和分类名称。
- 搜索结果使用单页连续列表，滚动接近底部时分批加载。
- 搜索历史支持查看和清除。
- 第一版只提供站内持久化通知和 WebSocket 实时提醒。
- 通知默认保留 90 天。

## 4. 技术选型声明

采用模块化单体架构，保留现有 Spring Boot、Vue 3、MySQL 和 WebSocket 技术栈。在同一应用和数据库中划分账号、商品搜索、结算、订单、支付、账户、配送、售后和通知模块，以本地事务保证核心一致性，并通过适配器隔离模拟支付、微信支付、模拟地图、百度地图和短信供应商。

不在当前阶段拆分独立支付微服务。当前项目规模下，微服务会引入分布式事务、消息中间件、服务发现和多服务部署成本，反而增加交易闭环的实现风险。各模块通过接口和事件边界解耦，为将来按业务压力拆分保留条件。

### 三项关键改进建议

1. 订单状态、支付状态、退款状态和售后状态必须独立建模，禁止继续用单一订单状态表达全部过程。
2. 所有资金变化必须通过不可修改的双向账本流水完成，账户余额只是流水汇总后的查询结果，并执行自动对账。
3. 支付、地图和短信等外部能力必须使用适配器接口，业务层不得直接依赖具体厂商工具类。

## 5. 总体架构

```text
Vue 用户端
├─ 账号与个人中心
├─ 菜单与跨分类搜索
├─ 地址与结算
├─ 支付结果确认
├─ 订单、时间轴与售后
└─ 通知中心
        │ HTTPS / WebSocket
        ▼
Spring Boot 模块化单体
├─ Identity：账号、短信验证、会话、个人资料
├─ Catalog：菜品、套餐、搜索、搜索历史
├─ Checkout：订单试算、费用、配送时间
├─ Order：订单、状态机、时间轴、取消
├─ Payment：支付单、退款单、渠道适配器
├─ Account：模拟账户、冻结余额、资金账本
├─ Delivery：地图适配器、距离、配送范围
├─ AfterSale：售后申请与审核
└─ Notification：通知、Outbox、WebSocket
        │
        ▼
MySQL + 可配置外部适配器
```

模块只通过明确的应用服务接口或持久化事件通信。Controller 不直接编排资金变动、状态转换或第三方调用。

## 6. 状态模型

### 6.1 订单状态

| 代码 | 状态 | 允许的主要操作 |
|---|---|---|
| 1 | `PENDING_PAYMENT` 待付款 | 支付、取消、超时关闭 |
| 2 | `PENDING_ACCEPTANCE` 待接单 | 用户取消、商家接单、商家拒单 |
| 3 | `PREPARING` 制作中 | 催单、申请取消、进入配送 |
| 4 | `DELIVERING` 配送中 | 申请售后、确认送达 |
| 5 | `COMPLETED` 已完成 | 24 小时内申请售后、再来一单 |
| 6 | `CANCELLED` 已取消 | 查询退款、再来一单 |

订单允许的主路径为：

```text
待付款 → 待接单 → 制作中 → 配送中 → 已完成
   └──────────────→ 已取消
```

制作中的取消申请处于待审核时，订单仍保持制作中；管理端必须先审批申请，不能直接将订单推进到配送中。配送中的售后获批后订单转为已取消并停止后续履约。已完成订单售后获批后仍保持已完成，通过售后和退款状态展示“已完成·已退款”。

### 6.2 支付状态

| 状态 | 含义 |
|---|---|
| `CREATED` | 已创建支付单，尚未发起渠道支付 |
| `PROCESSING` | 渠道处理中，禁止重复支付和取消 |
| `SUCCEEDED` | 支付成功，资金已进入平台待结算账户 |
| `FAILED` | 本次支付失败，可重新创建支付尝试 |
| `CLOSED` | 支付单已关闭，不得再次成功 |

同一订单允许存在多次失败的支付尝试，但最多只能有一笔成功支付。支付成功由服务端支付处理结果驱动，前端不能根据跳转参数自行判定。

### 6.3 退款状态

| 状态 | 含义 |
|---|---|
| `CREATED` | 已生成退款单 |
| `PROCESSING` | 退款来源资金已冻结，渠道处理中 |
| `SUCCEEDED` | 退款资金已进入用户模拟账户 |
| `FAILED` | 退款失败，来源资金保持冻结，可重试 |

退款失败时订单可以是已取消，但用户界面必须显示“退款失败”或“退款处理中”，不得显示“已退款”。累计退款金额不得超过订单实付金额。

### 6.4 取消与售后状态

| 状态 | 含义 |
|---|---|
| `PENDING_REVIEW` | 等待商家审核 |
| `APPROVED` | 商家批准，准备退款 |
| `REJECTED` | 商家拒绝并记录原因 |
| `REFUND_PROCESSING` | 已发起退款 |
| `COMPLETED` | 退款成功，申请处理完成 |
| `REFUND_FAILED` | 退款失败，等待系统或管理端重试 |

申请类型分为 `CANCEL_REQUEST` 和 `AFTER_SALE_REFUND`。订单状态决定用户能发起的申请类型，服务端不接受前端自行指定越权状态。

## 7. 资金模型

### 7.1 金额表示

所有新增交易和账本金额使用整数“分”存储，数据库类型为 `BIGINT`。现有订单 `DECIMAL` 金额在迁移阶段回填到 `amount_cent`，业务切换后由 `amount_cent` 作为权威金额；旧字段只在兼容期用于旧接口读取，不参与资金计算。

### 7.2 账户类型

| 账户类型 | 用途 |
|---|---|
| `USER` | 用户模拟支付账户 |
| `PLATFORM_PENDING` | 平台待结算账户 |
| `MERCHANT` | 商家模拟结算账户 |

账户保存可用余额和冻结余额。资金变化通过统一转账服务完成，禁止业务代码直接修改余额。

### 7.3 资金流

```text
支付成功：用户可用余额 → 平台待结算可用余额
退款准备：退款来源可用余额 → 退款来源冻结余额
退款成功：退款来源冻结余额 → 用户可用余额
订单完成：平台待结算可用余额 → 商家可用余额
```

待接单、制作中或配送中取消时，退款来源是平台待结算账户。订单完成后的售后退款来源是商家账户。第一版不提供商家提现，确保售后有效期内退款来源可用。

### 7.4 双向账本

每次资金转移生成一条资金转移记录和至少两条账本分录：来源账户为负向分录，目标账户为正向分录，同一转移号下分录金额之和必须为零。账本分录禁止修改和删除；纠错使用反向分录。

每日对账检查：

- 每笔转移的分录净额为零。
- 账户当前余额等于历史分录汇总。
- 支付成功总额等于进入平台待结算账户的金额。
- 退款成功总额不超过对应支付成功金额。
- 已完成未退款订单的结算金额与商家入账一致。

## 8. 支付渠道设计

### 8.1 统一接口

```text
PaymentGateway
├─ createPayment
├─ queryPayment
├─ closePayment
├─ createRefund
├─ queryRefund
└─ verifyAndParseCallback

实现：
├─ MockPaymentGateway
└─ WeChatH5PaymentGateway
```

业务层只识别统一的渠道结果和交易状态。支付渠道通过配置切换，订单、退款、通知和前端结果查询接口不随渠道改变。

### 8.2 生产级模拟支付

- 默认异步处理支付，创建支付后返回 `PROCESSING`。
- 模拟网关在可配置延迟后产生成功、失败或超时结果。
- 普通用户默认走成功路径；异常结果只能由自动化测试或受权限保护的管理端测试工具触发。
- 回调携带唯一事件 ID，重复回调不得重复扣款。
- 余额不足在扣款事务内判断并返回稳定错误码。
- 支付成功、账户扣款、双向流水、订单转待接单和时间轴记录在同一本地事务中完成。
- 支付超时、用户取消和支付结果处理使用期望状态条件更新，确保只有一个终态成功。

### 8.3 未来微信 H5 支付

未来接入微信 H5 时新增 `WeChatH5PaymentGateway`，保留现有业务层和前端查询流程：

```text
创建支付单 → 返回 H5 支付地址 → 浏览器唤起微信
→ 微信异步回调 → 服务端验签与更新 → 结果页查询服务端
```

微信 H5 回调或主动查询结果是支付事实来源，用户返回页面不代表支付成功。检测到微信内置浏览器时提示用户在系统浏览器打开；第一版不引入微信 OAuth 和 JSAPI 支付。

## 9. 结算试算与下单

### 9.1 试算流程

用户进入结算页、切换地址、配送方式或配送时间时调用订单试算接口。服务端返回：

- 当前有效商品和失效商品。
- 服务端单价、数量、商品小计和价格变化。
- 打包费、配送费、优惠金额和应付总额。
- 地址解析结果、配送距离和可配送状态。
- 门店营业状态。
- 立即配送预计送达时间或可预约时间段。
- 有效期为 5 分钟的 `previewToken`。

`previewToken` 是服务端签名的购物车、地址、费用规则和配送时间快照摘要，用于识别用户确认内容是否变化，不是免校验凭证。

### 9.2 正式提交

提交订单必须携带 `previewToken` 和请求幂等键。服务端重新查询购物车、商品、门店、地址和配送规则：

- 结果一致：创建订单和订单明细快照，清空购物车。
- 价格变化：返回变更商品和新金额，要求重新确认。
- 商品下架：返回失效商品并保留其他购物车内容。
- 门店打烊：阻止下单并保留购物车。
- 地址超范围：阻止下单并允许更换地址。
- 地图服务不可用：阻止下单并提供重新校验入口。

相同用户、相同幂等键的重复请求必须返回同一订单结果，不能重复创建订单。

### 9.3 配送时间

- 立即配送时间由服务端根据当前时间、基础制作时长和距离附加时长计算。
- 预约时间按 30 分钟一个时间段生成，只返回门店营业时间内且不早于最早送达时间的选项。
- 门店营业时间、基础制作时长、距离附加时长和可预约天数配置化。
- 服务端拒绝前端提交的过期时间、非候选时间段或营业时间外时间。

## 10. 地图与地址

### 10.1 地图适配器

```text
DeliveryMapGateway
├─ geocode
├─ calculateDrivingDistance
└─ healthCheck

实现：
├─ MockMapGateway
└─ BaiduMapGateway
```

模拟地图提供固定测试语义：

- 测试路 1 号：1.5 公里。
- 测试路 2 号：4.2 公里。
- 测试路 3 号：6.5 公里。
- 无效地址：地理编码失败。
- 超时地址：模拟服务超时。

百度地图 AK 通过环境变量注入，不写入源码。调用设置连接和读取超时，短暂错误只做有限重试；超过重试上限返回可恢复的业务错误，不跳过校验。

### 10.2 地址数据

- 省、市、区采用本地行政区划数据三级联动。
- 用户填写街道、门牌号、楼层和房间号等详细地址。
- 地址保存经纬度、地理编码状态、地图来源、校验时间和配送规则版本。
- 地址列表显示可配送、超出范围或待重新校验。
- 修改地址后原校验结果立即失效并重新解析。
- 订单创建时保存完整地址、联系人和电话快照。
- 地址查询、修改、删除和设默认地址全部校验当前用户归属。

## 11. 正式账号与个人资料

### 11.1 注册和认证

- 注册字段：手机号、短信验证码、用户自设密码和昵称。
- 登录方式：手机号与密码。
- 找回密码、换绑手机号和无当前密码修改密码必须短信验证。
- 密码使用 BCrypt，工作因子默认 12 并允许配置。
- 连续 5 次登录失败后锁定 15 分钟；成功登录后清零失败计数。
- 短信验证码有效期 5 分钟，同一手机号 60 秒内不能重复发送。
- 短信验证码只能使用一次，验证成功或超过有效期后失效。
- 开发环境使用模拟短信适配器，生产环境可切换短信供应商。

### 11.2 会话

- Access Token 有效期 15 分钟，只保存在前端内存中。
- Refresh Token 有效期 30 天，以 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie 保存。
- 页面刷新时通过刷新接口恢复 Access Token。
- 支持退出当前设备和退出全部设备。
- 修改密码、手机号或检测到高风险登录后撤销全部 Refresh Token。
- 现有 `localStorage` Token 在切换期只用于完成一次会话迁移，迁移后删除。

### 11.3 个人资料

- 支持昵称和头像编辑。
- 头像通过服务端上传接口保存，不接受用户直接填写外部 URL。
- 支持手机号换绑和密码修改。
- 身份证号不进入普通用户注册和资料页面。
- 昵称、头像、手机号、密码等敏感变更写入审计日志。

## 12. 跨分类搜索

- 服务端统一返回菜品和套餐，只包含启售商品。
- 搜索范围包括商品名称、描述和分类名称。
- 第一版使用数据库索引、规范化关键词和模糊查询，不引入独立搜索引擎。
- 返回不透明游标、固定批次大小和 `hasMore`，前端不显示页码。
- 前端使用 `IntersectionObserver` 在底部哨兵进入视口时加载下一批。
- 加载期间禁止重复请求，新结果按商品类型和商品 ID 去重。
- 请求失败时保留已有结果，并显示“点击重试”。
- 到达末尾显示“已经到底了”。
- 从商品详情返回时恢复搜索词、已加载结果和滚动位置。
- 游客搜索历史保存在浏览器；登录用户搜索历史保存在服务端并支持跨设备同步和清除。

## 13. 订单时间轴、取消与售后

每次订单、支付、退款和售后状态变化都写入不可修改的时间轴事件，包含事件类型、展示文案、操作者类型、操作者 ID、业务时间和关联业务号。

订单详情组合展示：

- 订单履约状态。
- 支付状态和实付金额。
- 取消或售后申请状态。
- 退款状态、退款金额和退款流水号。
- 完整时间轴。

用户操作规则：

- 待付款取消：关闭未完成支付单并取消订单。
- 待接单取消：取消订单、创建退款单并冻结退款来源资金。
- 制作中申请取消：创建待审核申请，订单暂不改变。
- 配送中申请售后：创建待审核申请。
- 已完成申请售后：以实际送达时间计算 24 小时窗口。
- 审核批准：创建或推进退款单，记录时间轴和通知。
- 审核拒绝：保存拒绝原因，订单继续原履约状态。
- 退款失败：保留冻结资金，通过同一退款单增加尝试次数并重试，不重复冻结。

## 14. 通知中心

业务事务内同时写入通知记录和 Outbox 事件。后台发布器读取未发布事件，发送 WebSocket 提醒并更新发布状态；失败采用指数退避重试，超过最大次数进入异常事件列表供管理端处理。

通知类型包括：

- 支付成功、失败和超时。
- 商家接单、拒单和取消。
- 用户取消申请的审核结果。
- 开始配送和配送完成。
- 退款处理中、退款成功和退款失败。
- 售后申请审核结果。

用户端支持：

- 查询通知列表和未读数量。
- 单条已读和全部已读。
- 点击通知进入对应订单详情。
- WebSocket 断线重连后补拉未读通知。

WebSocket 消息只用于提示数据变化，通知接口和订单详情接口是最终事实来源。客户端按事件 ID 去重。

## 17. 错误处理与用户恢复

| 场景 | 服务端行为 | 用户端行为 |
|---|---|---|
| 余额不足 | 支付失败且不产生资金流水 | 显示差额和领取模拟金入口 |
| 重复支付 | 返回原支付单或“已支付”结果 | 跳转订单详情，不重复扣款 |
| 支付处理中 | 返回当前支付单状态 | 显示确认中并轮询 |
| 前端响应丢失 | 支付状态仍由服务端保存 | 使用支付号恢复查询 |
| 支付超时 | 关闭支付单并条件取消订单 | 显示超时并提供再来一单 |
| 价格变化 | 拒绝旧试算提交 | 展示差异并重新确认 |
| 商品下架 | 返回失效商品 | 保留购物车并提示移除 |
| 门店打烊 | 阻止创建订单 | 保留购物车并提示营业状态 |
| 地址超范围 | 返回距离和范围错误 | 引导更换地址 |
| 地图超时 | 不跳过配送校验 | 保留表单并提供重试 |
| 退款失败 | 保持退款失败和资金冻结 | 展示原因与处理状态 |
| WebSocket 断线 | 通知仍持久化 | 重连并补拉未读通知 |
| 搜索加载失败 | 游标不前移 | 保留结果并提供重试 |

## 18. 安全与一致性

- 所有订单、支付、退款、地址、通知和流水接口校验当前用户归属。
- 支付和退款状态转换使用“主键 + 期望状态”条件更新。
- 账户余额更新使用数据库行锁或版本号，并在同一事务写入账本。
- 支付和退款回调使用唯一事件 ID 与渠道交易号双重幂等。
- 外部回调在真实微信渠道下必须验签、解密并校验金额和商户号。
- 短信验证码只保存摘要，不记录明文。
- Refresh Token 只保存不可逆摘要，原文仅通过安全 Cookie 传输。
- 头像上传限制文件类型、文件大小和图像尺寸，并生成服务端文件名。
- 日志不得记录密码、验证码、完整 Token、身份证号或完整支付敏感数据。

## 20. 分阶段实施边界

## 21. 迁移与兼容策略

1. 先增加新表、新字段和适配器，不删除旧接口。
2. 回填现有订单金额分字段，并校验回填前后金额一致。
3. 新前端切换到试算、支付查询和新会话接口。
4. 观察新链路运行和自动对账结果，确认无旧客户端依赖后停用演示登录接口。
5. 删除旧支付结果 URL 判定、固定 0.01 元退款和未配置地图时跳过校验的旁路。
6. 保留数据库迁移脚本和可验证的回滚脚本；资金流水表只允许前向修复，不做破坏性回滚。

## 22. 验收结果定义

项目完成时，普通手机浏览器用户能够：

1. 使用正式手机号账号安全注册、登录和找回密码。
2. 搜索并选择商品，管理准确且经过配送校验的地址。
3. 查看权威试算结果并创建唯一订单。
4. 使用可见的模拟账户完成支付并查看资金流水。
5. 在网络中断、重复点击或页面关闭后恢复支付结果。
6. 查询订单完整履约时间轴并收到可补拉的状态通知。
7. 按业务规则取消订单或申请售后。
8. 在退款成功后看到模拟余额按实付金额完整返还。

系统能够证明每一笔支付、结算和退款都有平衡账本，重复请求不会导致重复扣款或退款，所有核心异常场景均有自动化测试覆盖。
