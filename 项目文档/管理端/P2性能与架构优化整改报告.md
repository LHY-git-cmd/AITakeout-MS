# P2 性能与架构优化整改报告

## 1. 整改概况

- 整改日期：2026-08-22
- 整改范围：订单分页查询、订单定时任务、数据库索引、订单服务职责拆分、依赖注入方式和循环依赖配置
- 未纳入范围：前端升级、支付业务规则调整、微信回调验签与密钥迁移、全项目字段注入改造

## 2. 整改结果总览

| 项目 | 改动前现象 | 原因 | 改动后现象 | 作用 |
| --- | --- | --- | --- | --- |
| 订单分页 | 一页 N 条订单执行 `1 + N` 次查询 | VO 组装时逐单查询明细 | 固定执行 2 次查询 | 消除 N+1，减少连接占用、网络往返和对象映射开销 |
| 管理端订单页 | 不返回明细集合时仍逐单查明细 | 菜品描述与明细查询耦合 | 一次批量查询后组装 `orderDishes`，仍不设置 `orderDetailList` | 保持接口兼容并降低查询次数 |
| 超时订单任务 | 查询一次后循环更新 N 次，且无批次上限 | 逐实体更新、过滤字段缺索引 | 每批固定 2 次 SQL，默认最多 200 条 | 减少数据库往返，控制事务规模，支持多实例互斥处理 |
| 数据库查询 | 状态时间筛选、明细关联缺少针对性索引 | 基线表仅依赖主键或非目标索引 | 新增 2 个复合/关联索引 | 缩小定时扫描范围，加速按订单 ID 查询明细 |
| 订单服务 | 单类约 698 行，同时处理查询、支付、地图、通知等职责 | 功能持续集中叠加 | 主服务 260 行，抽取 4 个内部服务 | 主服务减少 438 行，约 62.8%，职责可独立测试和演进 |
| 依赖注入 | P2 涉及组件使用字段注入，全局允许循环依赖 | 依赖在运行时注入，潜在依赖环被兼容开关隐藏 | 涉及组件使用 `final` 构造器注入，删除循环依赖开关 | 依赖显式、对象可直接构造，启动阶段即可发现依赖环 |

## 3. 订单分页 N+1 优化

### 3.1 改动前现象与原因

订单主表完成分页后，旧实现针对每条订单调用一次 `getByOrderId`。用户端需要明细集合，管理端虽然不返回明细集合，但仍需拼接 `orderDishes`，因此两个入口都存在 N+1 查询。

根因是 VO 装配以单个订单为处理单位，没有先批量获取本页所有订单明细。

### 3.2 整改内容

- `OrderDetailMapper` 增加 `getByOrderIds`。
- MyBatis 使用受分页大小约束的 `order_id IN (...)` 一次获取本页明细。
- `OrderQueryService` 按 `orderId` 在内存分组并批量装配 VO。
- 空页直接返回，不生成无效的 `IN ()` SQL。
- 单订单详情仍使用精确查询，管理端列表继续只返回 `orderDishes` 而不设置 `orderDetailList`。

### 3.3 前后数据与作用

| 页面订单数 N | 改动前查询次数 | 改动后查询次数 | 减少比例 |
| ---: | ---: | ---: | ---: |
| 10 | 11 | 2 | 81.8% |
| 100 | 101 | 2 | 98.0% |
| 200 | 201 | 2 | 99.0% |

查询次数由随页大小线性增长的 `1 + N` 变为固定 2 次，主要降低数据库连接占用、网络往返和 MyBatis 映射开销。该比例是基于 Mapper/SQL 调用次数的确定性计算，不等同于生产环境响应时间提升比例。

## 4. 定时任务批处理与索引

### 4.1 改动前现象与原因

旧任务先查询全部候选订单，再循环执行条件更新。积压 N 条时需要 `1 + N` 次 SQL，候选集合没有上限，可能形成长事务和较高内存占用。`orders(status, order_time)` 与 `order_detail(order_id)` 也缺少明确索引。

根因是任务以实体为更新粒度，未采用有界批次；数据库结构没有针对实际过滤和关联条件建立索引。

### 4.2 整改内容

- 增加 `sky.order-task.batch-size`，默认值为 200，可通过 `ORDER_TASK_BATCH_SIZE` 调整。
- 在事务中按状态、时间和批次上限执行有序查询，并使用 `FOR UPDATE` 锁定本批订单。
- 使用一次 `UPDATE ... WHERE status = ? AND id IN (...)` 完成本批状态转换。
- 校验实际更新行数，不一致时抛出异常并回滚；成功后再发送通知。
- Flyway 与部署兼容 SQL 同步增加：
  - `idx_orders_status_order_time(status, order_time)`
  - `idx_order_detail_order_id(order_id)`

### 4.3 前后数据与作用

| 单批订单数 N | 改动前 SQL 次数 | 改动后 SQL 次数 | 减少比例 |
| ---: | ---: | ---: | ---: |
| 10 | 11 | 2 | 81.8% |
| 100 | 101 | 2 | 98.0% |
| 200 | 201 | 2 | 99.0% |

默认 200 条一批时，SQL 调用由 201 次降至 2 次。批次上限控制单事务工作量；联合索引匹配状态和时间过滤；行锁与期望状态条件避免多实例重复转换同一订单。

## 5. 服务职责与依赖结构

### 5.1 改动前现象与原因

`OrderServiceImpl` 约 698 行，直接依赖 8 个组件，在一个类中同时实现下单、分页与 VO 装配、支付退款、地图 API、状态流转和 WebSocket 通知。修改任一外部集成逻辑都需要进入订单主服务，测试也依赖反射设置内部配置。

根因是业务能力随需求增长持续堆叠，缺少按职责划分的内部服务边界。

### 5.2 整改内容

- `OrderQueryService`：分页、详情、批量明细和 VO 装配。
- `OrderPaymentService`：真实/模拟支付、支付成功回调和退款调用。
- `DeliveryRangeService`：完整地址、百度地图解析和配送距离校验。
- `OrderNotificationService`：来单、状态与催单通知，以及事务提交后发送。
- `OrderServiceImpl`：保留对 Controller 的兼容门面、下单和订单状态流转编排。
- `OrderTask`、`WebMvcConfiguration`、两个 JWT 拦截器及订单内部服务使用构造器注入。
- 删除 `spring.main.allow-circular-references=true`。

### 5.3 实际效果

| 指标 | 改动前 | 改动后 | 结论 |
| --- | ---: | ---: | --- |
| `OrderServiceImpl` 行数 | 约 698 | 260 | 减少 438 行，约 62.8% |
| 主服务直接依赖总数 | 8 | 8 | 数量未下降，指标部分达成 |
| 主服务基础设施依赖 | 8 | 4 个 Mapper | 支付、地图、通知等基础设施被内部服务封装 |
| P2 涉及 5 个既有组件中的 `@Autowired` | 16 处 | 0 处 | 构造器注入完成 |
| 循环依赖兼容开关 | 开启 | 删除 | 应用上下文仍正常启动 |

直接依赖总数没有下降，不能将该项描述为数量优化；改进点在依赖层级和职责语义：主服务不再直接依赖微信支付、用户查询、地图 HTTP 和 WebSocket 实现。后续若继续降低门面依赖数，可再抽取下单/复购命令服务，但不属于本次 P2 范围。

## 7. 剩余风险与后续验证

1. 当前数据为 SQL 调用次数与自动化测试结果，尚未在真实 MySQL 数据量和并发流量下执行压测；上线前应对典型页大小和任务积压量做 P95/P99、锁等待和慢查询对比。
2. 测试环境关闭了 Flyway。生产环境首次启用迁移前应确认既有 schema history 与 baseline 状态，并在备份库演练，避免已有索引或历史表结构造成迁移冲突。
3. 批量任务的 `FOR UPDATE` 依赖 InnoDB；部署库需保持该存储引擎，并结合实例数量观察锁等待后调整批次大小。
4. 微信回调验签、密钥迁移等 P0 问题不在本次范围内，不能因本次支付服务拆分而视为已解决。
5. 外部退款成功与本地事务提交之间仍存在分布式一致性窗口，后续需要退款单、幂等状态和补偿任务处理。
