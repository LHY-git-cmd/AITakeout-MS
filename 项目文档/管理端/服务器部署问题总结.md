# 苍穹外卖服务器部署问题总结

## 1. 部署概况

- 部署时间：2026-08-15
- 服务器系统：Alibaba Cloud Linux 3
- Web 服务器：Nginx 1.30.4
- 后端：Spring Boot 3，Java 21，监听 `8080`
- 前端：Vue 构建后的 `dist` 静态文件
- 数据库：MySQL 5.7，数据库名 `sky`
- 缓存：Redis，监听 `127.0.0.1:6379`，使用数据库 `10`
- 前端访问地址：`http://8.163.64.227`

最终请求链路：

```text
浏览器
  |
  | HTTP :80
  v
Nginx
  |-- /       -> /www/wwwroot/sky/dist
  |-- /api/   -> http://127.0.0.1:8080/admin/
  `-- /ws/    -> http://127.0.0.1:8080/ws/
                         |
                         v
                 Spring Boot + MySQL + Redis
```

## 2. 遇到的问题及解决过程

> 以下新增条目记录后续部署过程中遇到的问题。所有密码、Token、微信 Secret 和 OSS 密钥均使用占位符，不写入本文档。

### 2.1 宝塔面板可访问，但公网网站无法访问

**现象**

- 宝塔面板的 `8888` 端口可以连接。
- 公网 IP 的 `80` 和 `443` 端口连接超时。
- 宝塔防火墙已经放行 `80`，但网站仍无法从公网访问。

**原因**

服务器存在两层端口控制：

1. 阿里云安全组，控制流量能否进入云服务器。
2. 宝塔/系统防火墙，控制进入服务器后的端口访问。

只放行宝塔防火墙不够，阿里云安全组也必须放行对应端口。

**解决方法**

在阿里云安全组的入方向放行 TCP `80`。使用 HTTPS 时还需放行 TCP `443`。

后端 `8080` 只供本机 Nginx 反向代理使用，不需要向公网开放。

### 2.2 后端默认加载了开发环境配置

**现象**

宝塔 Java 项目显示加载的是 JAR 包内的 `application-dev.yml`，其中使用开发环境数据库：

```text
database: sky_take_out
username: root
```

服务器实际应连接生产数据库 `sky`。

**原因**

JAR 包内的 `application.yml` 设置了：

```yaml
spring:
  profiles:
    active: dev
```

`dev` 并不天然比 `prod` 优先，只是当前配置明确将 `dev` 设置为活动环境。

**解决方法**

在启动命令中显式激活生产环境：

```bash
/usr/bin/java -Xms256M -Xmx256M \
  -jar /www/wwwroot/sky/config/sky-server.jar \
  --spring.profiles.active=prod
```

不直接修改 JAR 包内的 `application-dev.yml`，避免重新打包或上传 JAR 后配置丢失，也避免生产密码进入 JAR。

### 2.3 激活 prod 后，数据源占位符无法解析

**现象**

应用启动时报错：

```text
Error creating bean with name 'dataSource'
${sky.datasource.driver-class-name}
```

随后 MyBatis 的 `sqlSessionTemplate`、Mapper、Service 和 Controller 连带创建失败。

**原因**

虽然指定了 `prod`，但 Spring Boot 没有找到服务器上的外部 `application-prod.yml`。Spring Boot 默认按进程工作目录查找外部配置，不保证自动查找 JAR 所在目录。

Controller 和 Mapper 报错不是根因，真正的根因是数据源配置未加载。

**解决方法**

在启动命令中明确增加外部配置目录，目录末尾保留 `/`：

```bash
/usr/bin/java -Xms256M -Xmx256M \
  -jar /www/wwwroot/sky/config/sky-server.jar \
  --spring.profiles.active=prod \
  --spring.config.additional-location=file:/www/wwwroot/sky/config/
```

外部生产配置文件位置：

```text
/www/wwwroot/sky/config/application-prod.yml
```

### 2.4 生产配置缺少阿里云 OSS 参数

**现象**

数据源问题解决后，应用继续启动，但出现：

```text
Failed to bind properties under 'sky.alioss.access-key-id'
Circular placeholder reference 'sky.alioss.access-key-id'
```

**原因**

基础 `application.yml` 使用同名占位符读取 `sky.alioss.*`，而外部 `application-prod.yml` 没有覆盖这些字段，形成循环占位符引用。

**解决方法**

暂时不使用 OSS 时，在 `application-prod.yml` 的 `sky` 节点下提供明确空字符串：

```yaml
sky:
  alioss:
    endpoint: ""
    access-key-id: ""
    access-key-secret: ""
    bucket-name: ""
```

不能使用 `##` 表示空字符串，因为 `#` 在 YAML 中表示注释。以上配置可以使应用启动，但图片上传功能不可用；启用图片上传时需要填写真实 OSS 参数。

### 2.5 Redis 密码与服务器实际配置可能不一致

**现象**

生产配置中曾填写 Redis 密码，但服务器本机 Redis 实际未设置密码。

**风险**

如果客户端配置了密码而 Redis 服务端没有密码，应用使用 Redis 时会发生认证错误。

**解决方法**

无密码时在 `application-prod.yml` 中设置空值：

```yaml
sky:
  redis:
    host: 127.0.0.1
    port: 6379
    password:
    database: 10
```

### 2.6 新应用启动时 8080 端口被占用

**现象**

```text
Web server failed to start. Port 8080 was already in use.
```

**原因**

旧的 Java 进程仍在运行，新进程无法再次监听 `8080`。

**解决方法**

先通过宝塔停止旧项目。如果端口仍被占用，在终端查询进程：

```bash
ss -lntp | grep ':8080'
ps -fp <PID>
```

确认 PID 属于旧的 `sky-server.jar` 后正常停止：

```bash
kill <PID>
```

没有直接使用 `pkill java`，避免停止服务器上的其他 Java 服务；也没有优先使用 `kill -9`，以便应用正常释放资源。

### 2.7 后端启动成功，但访问网站返回 Nginx 404

**现象**

浏览器访问公网 IP 后显示：

```text
404 Not Found
nginx
```

**原因**

Java 后端启动成功只代表 API 服务可用。首页由 Nginx 提供，Nginx 当时没有把 `/` 指向前端 `dist/index.html`，或者公网 IP 没有匹配到正确站点。

**解决方法**

- 创建并启用 HTML 站点。
- 绑定公网 IP `8.163.64.227`。
- 将站点根目录设置为 `/www/wwwroot/sky/dist`。
- 配置 Vue 路由回退以及 API、WebSocket 反向代理。

当前生效的核心配置为：

```nginx
server {
    listen 80;
    server_name 8.163.64.227;

    root /www/wwwroot/sky/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080/admin/;
    }

    location /ws/ {
        proxy_pass http://127.0.0.1:8080/ws/;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

修改后测试并重载 Nginx，网站可以正常打开。

### 2.8 MySQL 9 导出的 SQL 无法导入 MySQL 5.7

**现象**

云端导入数据库时报错：

```text
ERROR 1273 (HY000): Unknown collation: 'utf8mb4_0900_ai_ci'
ERROR 1146 (42S02): Table 'sky.address_book' doesn't exist
```

**原因**

本机数据库是 MySQL 9.5，导出文件使用了 MySQL 8/9 的 `utf8mb4_0900_ai_ci` 排序规则；服务器是 MySQL 5.7，不认识该排序规则。后续的 `1146` 是建表失败后的连带错误。

**解决方法**

重新导出时关闭 GTID：

```powershell
mysqldump -uroot -p --default-character-set=utf8mb4 `
  --single-transaction --routines --triggers `
  --set-gtid-purged=OFF `
  --result-file=sky_take_out_deploy.sql sky_take_out
```

再将高版本字符集转换为 MySQL 5.7 可识别的名称：

```text
utf8mb4_0900_ai_ci -> utf8mb4_unicode_ci
utf8mb3            -> utf8
utf8mb3_bin        -> utf8_bin
```

最终使用 `sky_take_out_deploy_compatible.sql` 导入云端。导入数据库名为 `sky` 时，后端 `sky.datasource.database` 也必须填写 `sky`。

### 2.9 Flyway 查询系统表权限不足

**现象**

```text
SELECT command denied to user 'sky'@'localhost'
for table 'user_variables_by_thread'
Unable to determine value for 'foreign_key_checks'
connection disabled
```

**原因**

数据库账号没有读取 `performance_schema.user_variables_by_thread` 的权限。`connection disabled` 和 `foreign_key_checks` 是 Flyway 初始化失败后的连锁错误。

**解决方法**

由于数据库已经导入完成，且当前 JAR 没有完整的 Flyway migration 资源，生产环境关闭 Flyway：

```yaml
spring:
  flyway:
    enabled: false
```

同时给业务账号授予业务库权限：

```sql
GRANT ALL PRIVILEGES ON `sky`.* TO 'sky'@'localhost';
GRANT ALL PRIVILEGES ON `sky`.* TO 'sky'@'127.0.0.1';
FLUSH PRIVILEGES;
```

只有在确实需要运行 Flyway 迁移时，才额外授予性能表的 `SELECT` 权限。

### 2.10 systemd 服务不存在

**现象**

```text
Failed to restart sky.service: Unit sky.service not found.
```

**原因**

服务器还没有创建 `/etc/systemd/system/sky.service`，或者项目是通过宝塔 Java 项目管理器启动的。

**解决方法**

若使用 systemd，创建服务文件后执行：

```bash
systemctl daemon-reload
systemctl enable sky
systemctl start sky
systemctl status sky --no-pager
```

宝塔 Java 项目管理器和 systemd 只能选择一种方式管理 JAR，不能同时启动同一个项目。

### 2.11 JAR 启动时 8080 端口被占用

**现象**

```text
Web server failed to start. Port 8080 was already in use
```

**原因**

旧的 Java 进程或宝塔项目已经监听 `8080`，systemd 再启动第二个实例就会失败。

**排查和解决方法**

```bash
systemctl stop sky
ss -lntp | grep ':8080'
ps -fp <PID>
```

确认是旧的 `sky-server.jar` 后正常停止：

```bash
kill <PID>
```

端口释放后再启动 systemd。不要使用 `pkill java`，避免误停其他 Java 服务；也不要一开始就使用 `kill -9`。

### 2.12 Windows Nginx 不能直接部署到 Linux 云服务器

**现象**

项目中有 `nginx.exe`，但云服务器系统是 Alibaba Cloud Linux。

**原因**

项目中的 Nginx 是 Windows 可执行文件，不能在 Linux 上运行。

**解决方法**

服务器重新安装 Linux 版 Nginx：

```bash
dnf install -y nginx
```

项目中的 `html/sky` 静态文件和 `/api/`、`/user/`、`/ws/` 代理规则可以复用，但 Linux 配置应使用绝对路径，例如：

```nginx
root /www/wwwroot/sky/dist;
proxy_pass http://127.0.0.1:8080/admin/;
```

### 2.13 Node.js 版本管理和前端依赖安装失败

**现象**

- Windows 没有安装 `nvm`，执行 `nvm install 14.21.3` 失败。
- 当前电脑默认 Node.js 是 24，而项目是 Vue 2、Vue CLI 3、webpack 4。
- `npm ci` 报 `fsevents` 的 `EINTEGRITY` 校验错误。
- `fibers@4.0.2` 安装时找不到 Visual Studio C++ 工具链。

**解决方法**

使用 Node.js 14.21.3 MSI 安装版，不必依赖 nvm。CMD 当前窗口临时切换：

```cmd
set "PATH=F:\develop\node\node-v14.21.3-msi\nodejs;%PATH%"
node --version
npm --version
```

安装依赖时使用官方 registry、独立缓存并跳过旧的安装脚本：

```cmd
npm ci --no-optional --ignore-scripts ^
  --registry=https://registry.npmjs.org ^
  --cache=E:\code\web-sky-project\.codex-tmp\sky-admin-npm-cache
npm run build
```

构建最终成功并生成 `dist`。构建输出中的大资源和 `node-fibers` 警告不影响本次产物生成，但后续应考虑升级前端依赖，移除已废弃的 `fibers`。

### 2.14 管理端和小程序的部署方式不同

管理端 Vue 项目通过 `npm run build` 生成 `dist`，上传到 Nginx 静态目录。

小程序目录 `WeChatProjects/miniprogram-1` 是已编译的微信小程序产物，不是可用 npm 重新构建的 uni-app 源码。其编译文件中曾写死：

```text
http://localhost:8080
```

发布前必须改为正式 HTTPS 域名，并通过微信开发者工具上传、审核和发布。服务器只提供小程序调用的 `/user/` 接口，不直接托管小程序代码。

## 5. 当前遗留事项

### 5.1 WebSocket 协议

当前网站使用 HTTP，但前端生产配置曾设置：

```text
wss://8.163.64.227/ws/
```

在未部署 HTTPS 证书的情况下，`wss://` 可能连接失败。临时测试方案是改为：

```text
ws://8.163.64.227/ws/
```

并重新构建、上传前端 `dist`。正式公网部署建议使用域名、HTTPS 和 WSS。

### 5.2 OSS 图片上传

OSS 参数当前为空时，应用可以启动，但菜品图片上传不可用。需要使用该功能时再配置真实的 OSS Endpoint、AccessKey 和 Bucket。

### 5.3 安全处理

- 部署过程中出现过面板、数据库、Redis 和微信相关明文凭据，部署稳定后应更换已经暴露的密码和密钥。
- `8080` 不需要对公网开放。
- SSH 和宝塔面板不宜长期允许所有公网 IP 访问，应限制可信来源 IP。
- 正式使用时应部署 HTTPS，避免 Token 和业务数据通过明文 HTTP 传输。

## 6. 本次部署结论

本次问题分别发生在云安全组、Spring Profile、外部配置加载、配置完整性、进程管理和 Nginx 站点配置等不同层级。排查时应从外到内依次确认：

```text
云安全组 -> 系统防火墙 -> Nginx -> 静态文件/反向代理
          -> Java 端口 -> Spring Profile -> MySQL/Redis
```

最终前端已能通过公网 IP 正常打开，Java 后端以生产配置运行，Nginx 已完成静态资源、管理端 API 和 WebSocket 路径的转发。
