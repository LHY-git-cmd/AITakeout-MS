# 苍穹外卖管理端 AI 助手第一阶段升级计划

## 1. 文档定位

本文档只规划苍穹外卖**管理端 AI 助手**的第一阶段升级工作，用于把当前已经跑通的 RAG 原型改造成可重复部署、可验证、可诊断的稳定系统。

第一阶段优先解决三个应用服务需要分别启动、环境依赖明显、配置不统一、真实模型调用缺少生产保护、质量缺少基线等问题。工具调用、长期记忆、自主规划和多 Agent 不在本阶段实施。

## 2. 已确认需求与边界

### 2.1 产品定位

- 使用主体：苍穹外卖管理端员工。
- 认证入口：Java 管理端 JWT。
- 权威业务数据源：Java 服务与 MySQL。
- Python Agent 只负责模型执行、RAG 检索、临时任务状态和事件输出，不直接成为业务数据权威源。
- 当前核心场景：员工基于授权知识库进行问答，并查看回答引用。

### 2.2 第一阶段包含

- 容器化 `sky-server`、`sky-agent`、`sky-embedding` 三个应用服务。
- 使用 Docker Compose 统一编排应用服务及其必要基础设施。
- 整理环境变量、密钥、模型文件和持久化数据的管理方式。
- 将现有真实 LLM 调用改造成可配置、可监控、可降级的稳定调用链路。
- 完善健康检查、日志、指标、故障处理和备份恢复说明。
- 建立 RAG 与 LLM 的最小离线评测集及发布回归门槛。
- 保留并扩展现有 Java、Python 与真实 RAG 端到端测试。

### 2.3 第一阶段不包含

- 不接入普通用户端 AI 助手。
- 不实现订单、退款、菜品修改等业务工具调用。
- 不实现长期用户画像或跨会话个性化记忆。
- 不引入 LangChain、LlamaIndex 等 Agent 框架重构核心链路。
- 不实现自主规划、多 Agent 协作或模型微调。
- 不以 Kubernetes 作为第一阶段交付目标。
- 不在本阶段改造管理端聊天页面的整体交互。

## 3. 前提检查与当前差距

### 3.1 已确认的现状

当前主链路已经具备以下基础：

```text
管理端提交问题
  -> Java 校验员工、会话和知识库权限
  -> Python Agent 异步执行任务
  -> BGE-M3 Embedding 服务生成向量
  -> Qdrant 检索授权知识
  -> 真实 LLM 或测试 Mock LLM 生成回答
  -> Python 输出结构化 SSE
  -> Java 持久化并向管理端转发 SSE
  -> 管理端展示回答和引用
```

- `sky-server` 默认端口为 `8080`。
- `sky-agent` 默认端口为 `8000`。
- `sky-embedding` 默认端口为 `8001`。
- RAG 依赖 Qdrant，Java 业务服务还依赖 MySQL 和 Redis。
- BGE-M3 模型约 4.27 GB，当前已在 CPU 环境完成验证。
- 真实 DeepSeek LLM 已接入，因此本阶段不是“首次接入真实 LLM”，而是完善其生产化能力。

### 3.2 需要修正的错误前提

1. **三个应用容器能够启动，不等于完整系统能够运行。** Compose 还必须处理 MySQL、Redis、Qdrant 的连接方式，或者允许连接到明确配置的外部实例。
2. **容器化不等于高可用。** 当前 Python 任务执行和部分状态仍有单实例限制，本阶段只保证单机 Compose 下的可重复部署与故障可诊断性。
3. **不能仅用 `depends_on` 保证服务可用。** Embedding 模型加载耗时明显，必须通过健康检查和启动重试处理依赖就绪顺序。
4. **BGE-M3 不应直接打入应用镜像。** 模型文件体积大，应通过只读卷挂载或独立模型卷提供，并固定模型 revision 与校验信息。
5. **“有端到端测试”不等于“质量达到上线标准”。** 当前测试主要证明链路连通，还需要带标准答案的检索与生成质量评测。

## 4. 技术选型声明

### 4.1 核心选型

1. 使用 Docker Compose 作为第一阶段统一启动入口，优先解决本地开发、测试和单机部署的一致性。
2. 三个应用分别构建镜像，应用镜像不包含密钥、运行数据、知识文档、向量数据和 BGE-M3 模型权重。
3. MySQL、Redis、Qdrant 在默认本地 Compose 中提供；同时允许通过环境变量连接外部托管实例。
4. Java/MySQL 继续作为会话、任务、消息和引用的业务权威来源。
5. LLM 保持 OpenAI 兼容客户端接口，但提供商、地址、模型和能力参数必须全部配置化。
6. 第一阶段保持 Python Agent 单实例执行约束，不通过增加 worker 数量伪装水平扩展能力。

### 4.2 三条最关键的改进建议

1. **先统一配置和密钥管理，再编写 Compose。** 否则只是把本机硬编码搬进容器，无法获得可移植部署能力。
2. **把健康检查、持久化卷和故障恢复作为容器化验收内容。** 验收不能只看容器处于 `running`，必须验证依赖真正就绪、重启后数据仍在。
3. **在继续增加 Agent 能力前建立质量基线。** 后续所有模型、Prompt、切块、阈值和检索策略变更都必须经过同一套回归评测。

## 5. 第一阶段目标架构

```text
管理端前端
    |
    v
sky-server :8080
    |-- MySQL :3306       业务权威数据、Flyway 迁移
    |-- Redis :6379       消息缓存等现有能力
    |
    v
sky-agent :8000
    |-- Qdrant :6333      知识向量
    |-- sky-embedding     语义向量生成
    |-- LLM API           回答生成
    v
sky-embedding :8001
    |
    `-- BGE-M3 只读模型卷
```

容器间不得继续使用 `localhost` 互相访问，应使用 Compose 服务名，例如：

- Java 调用 Agent：`http://sky-agent:8000`
- Agent 调用 Embedding：`http://sky-embedding:8001`
- Agent 调用 Qdrant：`http://qdrant:6333`
- Java 连接 MySQL：`mysql:3306`
- Java 连接 Redis：`redis:6379`

宿主机端口只用于开发调试；生产部署应仅暴露实际需要的入口。

## 6. 实施模块

### 模块一：配置、密钥与日志安全整改

#### 工作内容

- 盘点 Java、Agent、Embedding、MySQL、Redis、Qdrant 和 LLM 所需配置。
- 新增不含真实密钥的 `.env.example`，说明必填项、默认值和用途。
- 将 Java 中的数据库密码、Redis 密码、JWT 密钥、第三方服务密钥等移出版本化配置文件。
- 统一 `LLM_PROVIDER`、`LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY` 的命名和实际读取逻辑。
- 移除 Python Agent 中写死的 DeepSeek 地址和模型依赖。
- 为开发、测试、Compose 和生产环境建立明确的配置覆盖顺序。
- LLM 日志默认不输出完整 Prompt、历史消息、知识库正文和员工相关数据；保留 `trace_id`、任务 ID、模型、耗时、状态、Token 数及脱敏错误摘要。
- 启动时校验关键配置，缺少密钥或地址时快速失败并给出明确错误。

#### 产出

- `.env.example`
- Compose 环境变量清单
- 配置与密钥管理说明
- 完整 Prompt 日志脱敏方案

#### 模块验收

- 仓库内不再保留可直接使用的真实密钥或弱默认生产密钥。
- 替换 LLM 地址和模型只需修改环境变量，无需改代码。
- 日志中不出现 API Key、JWT、数据库密码和完整对话正文。

### 模块二：三个应用服务容器化

#### `sky-server`

- 使用 Java 21 多阶段构建镜像。
- 构建阶段执行 Maven 打包，运行阶段只保留必要 JRE 和应用产物。
- 使用非 root 用户运行。
- 通过环境变量连接 Agent、MySQL 和 Redis。
- 提供可用于容器健康检查的应用健康端点。
- 明确 JVM 内存参数和容器资源上限的配置入口。

#### `sky-agent`

- 构建独立 Python 镜像并安装固定版本依赖。
- 使用单进程运行，保留当前任务状态模型的一致性。
- 为任务状态 SQLite、知识文件等运行数据配置持久化卷。
- 提供存活检查和就绪检查；就绪检查应验证应用初始化完成，并能区分 Qdrant 或 Embedding 不可用。
- 容器关闭时停止接收新任务，并在限定时间内完成或终止当前任务。

#### `sky-embedding`

- 构建不含 BGE-M3 权重的 Python 运行镜像。
- 通过只读卷挂载模型目录，禁止启动时静默下载未经固定版本的模型。
- 支持 CPU 环境，预留通过环境变量选择 CUDA 的能力，但本阶段不承诺 GPU 镜像。
- 健康状态至少区分 `starting`、`healthy` 和 `failed`。
- 模型完成加载后才进入就绪状态。

#### 模块验收

- 三个镜像能够独立构建。
- 镜像内不含 `.env`、密钥、本地数据库、知识源文件或模型权重。
- 容器使用非 root 用户运行。
- 删除并重新创建应用容器后，挂载的数据仍可恢复。

### 模块三：Docker Compose 统一编排

#### 工作内容

- 新增根目录 `compose.yml`，统一编排：
  - `sky-server`
  - `sky-agent`
  - `sky-embedding`
  - `mysql`
  - `redis`
  - `qdrant`
- 为 MySQL、Redis、Qdrant、Agent 和 Embedding 配置命名持久化卷。
- BGE-M3 使用宿主机目录或预创建模型卷，以只读方式挂载。
- 所有服务配置健康检查、合理的重启策略和日志大小限制。
- 依赖服务通过健康状态和应用自身重试共同处理启动顺序。
- 提供两种部署模式：
  - 默认本地完整模式：Compose 启动三个应用及全部基础设施。
  - 外部基础设施模式：应用通过环境变量连接现有 MySQL、Redis、Qdrant。
- 将数据库初始化交给现有 Flyway，禁止用手工 SQL 作为正常启动前置步骤。
- 文档说明首次加载 BGE-M3 所需时间、内存和磁盘要求。

#### 模块验收

在已准备模型文件和合法环境变量的前提下：

```powershell
docker compose up -d --build
docker compose ps
```

应满足：

- 所有必需服务最终进入健康状态。
- Java 能连接 MySQL、Redis 和 Python Agent。
- Agent 能连接 Qdrant、Embedding 和真实 LLM。
- 从管理端提交问题后能够收到 SSE 回答及引用。
- 执行 `docker compose restart` 后，MySQL、Qdrant 和必要任务数据未丢失。
- 单个依赖延迟启动时，系统不会因一次连接失败永久不可用。

### 模块四：真实 LLM 调用生产化

#### 工作内容

- 统一同步与流式请求的模型配置和错误处理。
- 配置连接超时、首 Token 超时、总超时和取消传播。
- 对可重试错误实施有限次数、带退避的重试；流式响应已输出内容后不得盲目重试并产生重复文本。
- 对限流、认证失败、模型不存在、内容审查、网络超时和服务端错误进行分类。
- 设置 Agent 级最大并发数和排队上限，超过容量时快速返回明确错误。
- 记录提示 Token、生成 Token、响应时间、首 Token 时间、模型和估算成本。
- 支持主模型和可选降级模型，但降级行为必须可配置并可在日志中识别。
- 对管理端知识问答使用低随机性默认参数，模型参数通过白名单控制。

#### 模块验收

- API Key 错误、限流、超时和模型不可用均有稳定且可识别的错误结果。
- 前端取消任务能够传递至 Java 和 Python，不继续无意义消耗模型 Token。
- 同一配置能够在本机运行和 Compose 运行之间切换。
- 能按天统计调用次数、Token、失败率、P50/P95 延迟和估算成本。

### 模块五：可观测性与运行可靠性

#### 工作内容

- 三个服务统一结构化 JSON 日志字段：时间、服务名、环境、级别、`trace_id`、`task_id`、`session_id`、事件和错误类型。
- Java 调用 Agent、Agent 调用 Embedding/LLM/Qdrant 时传递或关联追踪标识。
- 第一阶段至少采集以下指标：
  - HTTP 请求量、错误率和延迟。
  - Agent 排队任务数、运行任务数、取消数和失败数。
  - LLM 首 Token 延迟、总延迟、Token 和错误分类。
  - RAG 有结果率、TopK 分数分布和拒答率。
  - Embedding 批大小、推理耗时、模型加载状态和失败数。
- 建立最小告警规则：服务不可用、连续 LLM 失败、错误率升高、任务积压、磁盘容量不足。
- 编写 MySQL、Qdrant 和 Agent 运行数据的备份与恢复步骤。
- 明确日志和对话数据保留期限，避免无限增长。

#### 选型边界

第一阶段先保证应用暴露标准指标和结构化日志。Prometheus、Grafana、Loki 可以作为 Compose 的可选观测 profile，不要求为了本地默认启动而强制增加全部组件。

#### 模块验收

- 能通过同一个 `task_id` 关联 Java、Agent、Embedding 和 LLM 的一次请求。
- 能从指标或日志判断故障位于 Java、Agent、Embedding、Qdrant 还是 LLM。
- 告警测试能够识别至少一次服务下线和一次连续模型调用失败。
- 按文档完成一次备份与恢复演练。

### 模块六：RAG/LLM 质量基线与回归测试

#### 工作内容

- 从管理端真实使用场景整理首批 50～100 条评测问题。
- 每条数据记录问题、授权知识库、期望答案要点、允许引用来源和是否应拒答。
- 覆盖以下类型：
  - 精确事实查询。
  - 同义表达和口语表达。
  - 多文档综合问题。
  - 无证据问题。
  - 越权知识库问题。
  - 文档中的恶意指令或 Prompt Injection。
- 建立指标：
  - `Recall@K` 和检索命中率。
  - 引用来源正确率。
  - 答案要点覆盖率。
  - 无证据拒答准确率。
  - 越权数据泄露数。
  - P50/P95 延迟和单请求 Token。
- 保留 Mock LLM 测试用于稳定验证协议；增加少量真实 LLM 回归测试用于验证实际生成质量和兼容性。
- 测试数据使用独立知识库和 Qdrant 集合或唯一标识，结束后自动清理。

#### 初始发布门槛

以下数值在首轮基线完成后可调整，但调整必须记录原因：

- Java/Python 单元与契约测试全部通过。
- 真实 Embedding + Qdrant + Mock LLM 端到端测试全部通过。
- 引用来源正确率不低于 90%。
- 无证据拒答准确率不低于 95%。
- 越权知识库访问测试必须 100% 拒绝。
- Prompt Injection 测试不得执行知识文档中的指令。
- 真实 LLM 调用成功率不低于 99%，不包含测试主动制造的故障。

### 模块七：启动、运维与故障处理文档

#### 工作内容

- 编写首次部署、日常启动、停止、升级和回滚步骤。
- 编写 BGE-M3 模型准备及校验说明。
- 编写环境变量说明和示例，不记录真实密钥。
- 编写常见故障排查：模型加载失败、Qdrant 集合维度不匹配、LLM 限流、SSE 中断、MySQL/Flyway 失败等。
- 提供健康检查、查看日志、执行测试、备份和恢复的命令。
- 记录当前单实例约束以及不能直接增加 Agent worker 的原因。

#### 模块验收

- 新环境按照文档能够完成首次启动，无需修改源代码或使用 Windows 特定绝对路径。
- 开发人员能在 15 分钟内根据文档定位一个模拟的依赖故障。
- 文档中的启动、测试、备份和恢复命令均经过实际验证。

## 8. 第一阶段总体完成定义

第一阶段只有在以下条件全部满足时才视为完成：

1. 三个应用均有可重复构建、最小化且不含敏感数据的镜像。
2. 一条 Docker Compose 命令可启动完整管理端 AI 助手后端链路。
3. 容器间不存在依赖宿主机 `localhost` 或 Windows 绝对路径的调用。
4. BGE-M3 模型、MySQL、Qdrant 及必要 Agent 数据使用明确的持久化方案。
5. 配置文件中不再保存真实密钥，LLM 请求日志完成脱敏。
6. LLM 调用具备超时、错误分类、并发限制、取消和指标记录。
7. 服务重启、依赖延迟启动和常见外部故障有测试或演练记录。
8. 管理端问答、RAG 引用、无证据拒答和知识库权限测试达到发布门槛。
9. 新环境能够严格按照文档完成部署、验证、备份和恢复。

## 9. 主要风险与应对

| 风险 | 影响 | 第一阶段应对 |
| --- | --- | --- |
| BGE-M3 体积大、CPU 加载慢 | Compose 启动时间长、健康检查误判 | 模型卷挂载、较长启动宽限期、独立 readiness |
| Python Agent 单实例 | 无法真正水平扩容 | 明确单实例约束，限制并发，不在本阶段上 K8s |
| SQLite 与本地知识文件 | 容器重建后可能丢失 | 命名卷、备份恢复演练、明确数据权威边界 |
| 完整 Prompt 进入日志 | 泄露内部知识和员工数据 | 默认脱敏，只保留诊断元数据 |
| LLM 外部服务不稳定 | SSE 中断或任务长时间占用 | 分层超时、有限重试、取消、熔断与降级配置 |
| Compose 同时启动多个依赖 | 冷启动顺序不稳定 | 健康检查、应用重试、幂等初始化 |
| 只验证链路不验证答案 | 系统可运行但回答不可靠 | 固定评测集和发布回归门槛 |

## 10. 后续阶段入口条件

第一阶段完成并稳定运行后，再根据管理端的实际需求规划第二阶段。第二阶段优先考虑的不是多 Agent，而是**只读业务工具调用**，例如查询订单、菜品、库存和运营数据。

进入第二阶段前必须满足：

- 第一阶段质量与可靠性指标连续达标。
- 已明确每个管理端角色可访问的数据范围。
- 已定义工具 Schema、超时、幂等、审计和错误语义。
- 已确认哪些操作只读，哪些操作需要审批或二次确认。

写操作、长期记忆、自主规划和多 Agent 应在只读工具调用稳定后分别评估，不作为当前路线的默认承诺。
