# P2 性能与架构优化计划

## 1. 目标与范围

本计划落实项目巡检中的 P2 性能与架构建议，范围限定为：

1. 消除订单分页查询的 N+1 问题。
2. 避免管理端订单列表在不返回明细集合时仍逐单查询明细。
3. 将订单超时定时任务从逐条更新改为有界批量处理，并补充必要索引。
4. 拆分过大的订单服务，明确查询、支付、配送校验和通知职责。
5. 将本次涉及的组件改为构造器注入，验证并关闭 Spring 循环依赖兼容开关。

本次不进行前端框架升级、不修改支付业务规则、不重构全部 67 处字段注入，也不处理 P0 中尚未完成的微信验签和密钥迁移。

## 2. 改动前基线

### 2.1 订单分页查询

- 用户端分页：先查询一页订单，再对每条订单执行一次 `getByOrderId`。
- 管理端分页：虽然 `includeDetails=false`，但 `buildOrderVO` 仍先执行 `getByOrderId` 以拼接菜品描述。
- 每页 N 条订单时，数据库查询次数为 `1 + N`。
- 当 `pageSize=10` 时为 11 次查询；`pageSize=100` 时为 101 次查询。

原因：订单 VO 的组装方法以单个订单为粒度查询明细，没有批量预取和内存分组。

### 2.2 定时任务

- 每次先查询 N 条候选订单，再循环执行 N 次条件更新。
- 每批 SQL 次数为 `1 + N`。
- 查询没有批次上限，订单积压时会在单事务中加载并更新全部记录。
- `orders` 表只有主键，缺少定时查询所需的 `(status, order_time)` 索引。
- `order_detail` 基线 SQL 未声明 `order_id` 索引。

原因：任务按实体逐条更新，数据库访问次数随积压量线性增长；过滤字段缺少联合索引。

### 2.3 服务结构与依赖

- `OrderServiceImpl` 约 686 行，直接依赖 8 个组件。
- 同时承担下单、订单查询、状态流转、支付/退款、地图距离校验和 WebSocket 通知。
- 项目有 35 个类、67 处字段注入。
- `spring.main.allow-circular-references=true` 会隐藏潜在依赖环。

原因：业务持续叠加在单个服务实现中，职责边界和依赖方向没有随功能增长调整。

## 3. 技术选型声明

### 3.1 批量明细查询

在 `OrderDetailMapper` 增加 `order_id IN (...)` 批量查询。分页拿到订单 ID 后只查询一次明细，并按 `orderId` 分组，再批量组装 VO。

选择理由：保持现有分页 SQL 和 VO 契约不变，改动范围小，数据库查询次数固定为 2。

### 3.2 有界批量定时任务

在事务内按状态和时间查询有限批次并加行锁，再使用 `id IN (...) AND status = ?` 一次更新。批次大小通过配置控制，默认 200。

选择理由：相比无锁批量更新，它仍能准确识别本实例取得处理权的订单，从而只向真正转换成功的订单发送通知；相比逐条更新，SQL 次数不再随 N 增长。

### 3.3 服务拆分方式

保留 `OrderService` 作为对 Controller 的兼容门面，抽取内部协作组件：

- `OrderQueryService`：分页、详情和 VO 批量组装。
- `OrderPaymentService`：支付准备、模拟支付、支付成功和退款调用。
- `DeliveryRangeService`：地址解析与配送距离判断。
- `OrderNotificationService`：事务提交后的来单和状态通知。

选择理由：不改 REST 接口和公开服务契约，同时降低核心实现的依赖数与单文件复杂度。

## 4. 三项关键改进建议

1. 性能优化必须用“查询次数恒定”作为验收条件，而不仅是代码看起来批量化；新增 Mockito 查询次数测试和 MyBatis 集成测试。
2. 定时任务必须设置批次上限和复合索引，避免积压时形成长事务；后续可根据监控调整批次大小。
3. 架构拆分以职责和依赖方向为边界，保留 `OrderService` 门面，避免 Controller 与接口大面积变更。

## 5. 实施模块

### 模块一：订单查询性能

改动：

- 增加批量明细查询接口和 SQL。
- 新增订单 VO 批量组装逻辑。
- 用户端和管理端分页统一使用批量组装。
- 单订单详情仍使用精确查询。
- 管理端列表不设置 `orderDetailList`，但继续保留 `orderDishes` 字段，确保前端兼容。

预期作用：

- 分页 SQL 次数由 `1 + N` 固定为 2。
- `pageSize=100` 时查询次数由 101 降至 2，理论查询调用减少约 98%。
- 避免数据库连接、网络往返和 MyBatis 映射开销随页大小线性增加。

验证：

- 测试 10 条订单只调用一次批量明细 Mapper。
- 测试管理端不返回明细集合但菜品描述保持一致。
- 验证空页不会执行无意义的 `IN ()` 查询。

### 模块二：定时任务与索引

改动：

- 增加有界、加锁的超时订单查询。
- 增加按 ID 集合和期望状态的批量更新。
- 增加 `sky.order-task.batch-size` 配置。
- 使用 Flyway 添加 `orders(status, order_time)` 和 `order_detail(order_id)` 索引；同时更新部署兼容 SQL。
- 通知对象只使用本事务锁定并完成转换的订单。

预期作用：

- 每批 N 条从 `1 + N` 次 SQL 降为固定 2 次。
- 200 条一批时由 201 次降至 2 次，理论 SQL 调用减少约 99%。
- 降低积压情况下的事务持续时间、内存占用和数据库扫描范围。
- 多实例运行时避免重复处理同一订单。

验证：

- Mapper 集成测试验证批量更新只修改期望状态。
- 任务单元测试验证一批只调用一次更新并准确通知。
- 使用 H2/MySQL 兼容测试验证 SQL；若 H2 不支持目标锁语法，则为测试环境提供等价 SQL 配置。

### 模块三：职责拆分与构造器注入

改动：

- 抽取订单查询、支付、配送距离和通知组件。
- `OrderServiceImpl` 保留业务编排与订单状态流转。
- 本次涉及的新旧组件改为 `final` 字段和构造器注入。
- 将 Web MVC 配置、JWT 拦截器和订单定时任务同步迁移为构造器注入。
- 删除 `spring.main.allow-circular-references=true`。

预期作用：

- 降低 `OrderServiceImpl` 行数和直接依赖数量。
- 单元测试可以按职责独立构造，不再依赖反射注入。
- 应用启动时立即暴露真实循环依赖，而不是运行期隐藏。
- 为后续支付回调验签、退款补偿和查询缓存提供稳定扩展点。

验证：

- 应用上下文在关闭循环依赖后成功启动。
- 现有 REST 接口和 `OrderService` 方法签名保持不变。
- 原有及新增订单测试全部通过。

### 模块四：对比验证与报告

- 执行 `mvn test` 全量测试。
- 执行查询次数、批量任务和应用上下文专项测试。
- 检查 MyBatis XML、Flyway 脚本和 Git 差异。
- 记录改动前后 SQL 次数、代码规模、依赖数量、问题原因、实际作用和剩余风险。
- 生成 `项目文档/P2性能与架构优化整改报告.md`。

## 6. 执行顺序

1. 模块一：订单查询 N+1 优化。
2. 模块二：定时任务批处理和索引。
3. 模块三：订单职责拆分、构造器注入和关闭循环依赖。
4. 模块四：全量验证与整改报告。

## 7. 风险与边界

- `IN` 查询必须受分页和任务批次上限控制，避免超长 SQL。
- 行锁批处理依赖 InnoDB；当前部署 SQL 已使用 InnoDB。
- Flyway 当前目录此前为空，首次新增迁移需验证现有生产库的 baseline 状态。
- 服务拆分不能改变事务边界，尤其是订单状态更新、退款和提交后通知。
- 工作树已有大量未跟踪前端文件和用户新增后端文件，本次不会删除、覆盖或格式化无关内容。
