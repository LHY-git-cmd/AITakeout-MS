## 二、操作流程

1. 管理员说“帮我添加一些菜品”，没有具体要求时，Agent 提示是否生成测试数据。
2. 明确同意测试后，Agent 查询真实分类，再随机设计三道不同的测试菜品；无分类时提示先创建分类。
3. 生成名称、价格、分类、描述、食材、过敏原及每份营养；图片可省略，口味可选。
4. 确认卡片展示菜品明细，食材、过敏原和营养可展开查看；管理员确认后才写入。
5. 创建结果包含菜品 ID、停售状态和图片待上传提示。取消、过期或未确认不创建记录。
6. 拒绝测试时，Agent 说明需要提供具体资料并追问缺失的必要字段。正式菜品只保存实际提供的信息，不凭空补齐营养数据。

测试意图识别、随机设计与缺失信息追问通过管理端专属系统提示实现；参数和落库规则由 Python 模型与 Java 校验共同约束。实际自然语言表现仍需使用部署后的模型进行手工验收。

## 三、后端实现

- 新增 Agent 专用 DTO，不修改原手工新增表单的图片必填规则。
- 新增菜品统一默认停售；图片为空时保存为空字符串。
- 测试营养来源必须为 `SIMULATED`，服务端写入明确的模拟来源与不确定性说明；沿用现有营养服务，审核状态保持 `DRAFT`。
- 校验名称、分类、价格精度、营养精度、嵌套字段、列表长度及过敏原状态。拒绝传入起售状态或实体 ID 等额外字段。
- 批次内同名菜品拒绝保存；已有同名菜品冲突时整批回滚。
- 准备阶段记录分类版本；执行事务按分类 ID 顺序加锁，并重新比对确认时的分类版本。
- 菜品、口味、营养、食材、过敏原、执行结果及确认完成状态在一个事务中提交或回滚。
- 确认记录保存创建结果，重复执行返回原结果，避免重复创建。

新增数据库迁移：`V20261007_01__persist_admin_dish_creation_result.sql`，给 `admin_agent_tool_confirmation` 增加可空的 `result_json` JSON 列。该迁移不修改原业务数据。

## 四、确认界面

沿用管理端 Agent 的原确认、取消和错误反馈机制。卡片增加每道菜品的价格、分类、图片状态、描述、口味，以及可展开的每份营养、食材、过敏原和来源说明。

营养口径：重量与宏量营养素为 g，热量为 kcal，钠为 mg。未知过敏原状态显示“未知”，不会显示为“不含”。界面沿用主题变量和原布局，增加键盘可聚焦的展开区及长文本换行。

## 六、部署后手工验收

1. 重新运行 `scripts/deploy-clean.ps1`，构建更新后的 Java、Agent 和管理端镜像；Java 启动时由 Flyway 应用新增迁移。
2. 在管理端准备至少一个启用的菜品分类。
3. 在管理端 Agent 输入“帮我添加一些菜品”，应先询问是否生成测试数据。
4. 回答“是”，应出现三道菜品的确认卡片，核对分类、价格、描述、食材、过敏原和营养数据。
5. 点击取消，确认没有新增菜品；重新发起并确认，检查菜品列表新增三道、均停售，营养待审核且来源为模拟。
6. 给新增菜品上传图片；根据实际配方核实资料，再决定审核和起售。
7. 另开会话回答“不是”，应提示提供具体资料；提供名称、真实分类与价格后，确认添加正式菜品，未提供的营养不应被编造。

如需撤回功能，可回退新增工具注册、操作分发与确认预览；保留新增的可空结果列，不需要删除已有菜品或确认记录。
