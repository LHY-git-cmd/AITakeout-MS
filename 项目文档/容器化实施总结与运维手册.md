# 苍穹外卖 AI 助手容器化实施总结与运维手册

## 1. 文档范围

本文总结 `sky-server`、`sky-agent`、`sky-embedding` 三个应用及 MySQL、Redis、Qdrant 基础设施的容器化过程，
记录实施期间出现的问题、原因、解决办法、容器化常见陷阱和日常运维方法。

当前 Compose 编排范围：

```text
sky-server      :8080
sky-agent       :8000
sky-embedding   :8001
mysql           :3306（容器内部）
redis           :6379（容器内部）
qdrant          :6333（容器内部）
```

本阶段仍是单机 Docker Compose 部署，不提供 Kubernetes、高可用集群或 Agent 多实例能力。

## 2. 容器化实施步骤

### 2.1 配置与密钥整理

1. 将数据库、Redis、JWT、LLM、Qdrant、Embedding 等配置统一为环境变量。
2. 使用 `.env.example` 提供变量名称、默认值和用途说明。
3. 真实 `.env` 只保存在部署机器，不提交 Git。
4. LLM 统一使用：

   ```text
   LLM_PROVIDER
   LLM_BASE_URL
   LLM_MODEL
   LLM_API_KEY
   ```

5. Agent 启动时校验关键配置，缺失时快速失败且不打印密钥内容。

### 2.2 应用镜像构建

#### sky-server

- 使用 Maven + Java 21 多阶段构建。
- 运行层只保留 JRE、curl 和应用 JAR。
- 以 `10001:10001` 非 root 用户运行。
- 创建并授权 `/app/data/knowledge`，用于 Java 上传知识文档。
- 提供 `/actuator/health/readiness` 健康检查。
- 支持 `JAVA_TOOL_OPTIONS` 和 30 秒优雅停机。

#### sky-agent

- 使用 Python 3.11 镜像和固定版本依赖。
- 只运行一个 Uvicorn worker，保持当前任务状态模型一致。
- `/app/data` 保存任务 SQLite、知识 SQLite 和知识源文件。
- 提供 `/health/live`、`/health/ready`。
- readiness 同时检查 Qdrant 与 Embedding。

#### sky-embedding

- 使用 Python 3.11 CPU 镜像。
- 模型权重不复制进镜像，通过 `/models/bge-m3` 只读挂载。
- 默认项目模型目录：

  ```text
  sky-embedding/models/bge-m3
  ```

- 提供 `starting`、`healthy`、`failed` 三种状态。
- 模型加载完成后 `/health/ready` 才返回 200。

### 2.3 Compose 编排

根目录 `compose.yml` 负责启动六个服务，并配置：

- 服务名网络通信，禁止应用间使用 `localhost`。
- `depends_on.condition: service_healthy` 依赖等待。
- `restart: unless-stopped`。
- JSON 日志轮转：单文件 10 MB，保留 3 个。
- MySQL、Redis、Qdrant、Agent、Server 命名卷。
- Embedding 模型宿主机目录只读绑定挂载。
- MySQL Flyway 在 Java 启动阶段执行迁移。

外部基础设施模式通过 `compose.external.yml` 覆盖外部地址，并通过非默认 profile 防止启动本地基础设施。

### 2.4 启动与验收

```powershell
docker compose -f compose.yml config --quiet
docker compose -f compose.yml up -d --build
docker compose -f compose.yml ps
```

验收顺序：

1. 六个服务最终为 `healthy`。
2. 检查 Java readiness、Agent readiness 和 Embedding readiness。
3. 登录管理端提交 AI 问答，确认 submit 和 SSE 事件流正常。
4. 上传知识文档并等待索引状态成功。
5. 重启容器后确认 MySQL、Qdrant 和 Agent 数据仍在。

## 3. 实施中遇到的问题

### 3.1 宿主机 3306 端口冲突

错误：

```text
ports are not available ... 0.0.0.0:3306 ... Only one usage of each socket address
```

原因：Windows 上已有 `mysqld.exe` 占用 3306。

处理：将宿主机映射改为 `13306:3306`。容器内部仍使用 `mysql:3306`，Java 无需改成 13306。

排查命令：

```powershell
Get-NetTCPConnection -LocalPort 3306 -State Listen
docker ps
```

### 3.2 Agent 缺少 LLM 配置

错误：

```text
invalid Agent configuration: LLM_PROVIDER is required; ...
```

原因：系统环境变量只在宿主机进程环境中存在，必须确认 Compose 渲染并将变量注入 Agent 容器；同时最初还缺少 `LLM_PROVIDER`。

处理：在项目 `.env` 中配置四个 LLM 变量，随后重新创建容器：

```powershell
docker compose up -d --force-recreate sky-agent
```

修改 Windows 环境变量后必须重新打开终端，并重新创建容器，已运行容器不会自动刷新环境。

### 3.3 Embedding readiness 启动阶段返回 503

现象：Agent 日志周期性出现：

```text
GET /health/ready 503 Service Unavailable
```

原因：BGE-M3 约 4.27 GB，CPU 加载需要几十秒甚至更久。

结论：这是正常的 `starting` 状态，不是故障。模型加载完成后应恢复 200。Compose 为 Embedding 设置较长 `start_period`，Agent 通过健康依赖等待。

### 3.4 Java 知识文档上传失败

错误：

```text
文档上传失败: /app/data
```

原因：Java 以非 root 用户运行，但 `/app/data/knowledge` 未在镜像中创建和授权。

处理：镜像创建 `/app/data/knowledge` 并授权给 `10001:10001`，Compose 增加 `server-data:/app/data` 持久化卷。

### 3.5 Java 调 Agent 返回 422，提示 body 缺失

错误：

```text
POST /api/v1/agent/submit 422
Field required: body
```

同时 Agent 日志出现：

```text
Unsupported upgrade request
Invalid HTTP request received
```

原因：Java 客户端在明文容器网络中尝试 HTTP/2 h2c 升级，Uvicorn 未按预期处理，导致 JSON body 未正确到达。

处理：

- 显式设置 `Content-Type: application/json`。
- Java `AgentClient` 使用 `SimpleClientHttpRequestFactory`，强制兼容 HTTP/1.1。
- 增加提交请求契约测试。

### 3.6 取消接口 404

现象：提交失败后出现：

```text
POST /api/v1/agent/tasks/{taskId}/cancel 404
```

原因：Java 在提交失败后执行尽力清理，但任务实际上从未成功写入 Agent 任务库，因此 Agent 返回 Task not found。

结论：这是提交失败的次生现象，不是 Agent 路由缺失。应先修复 submit 根因。

### 3.7 AI 返回“没有足够信息”

原因：知识文档索引失败或没有可用版本时，Java 会传递空的 `document_versions`；Agent 按设计拒答，不调用 LLM。

此外，“今天的订单情况”属于实时业务查询，需要只读业务工具调用；当前 RAG 阶段不具备直接查询订单的能力。

正确处理：先将文档重建索引，确认文档状态成功，再用文档中明确存在的问题测试。

### 3.8 SSE 面板显示“无法加载响应数据”

原因：浏览器开发者工具对已经正常结束的 SSE 请求可能显示“请求已完成”，不等于请求失败。

判断依据：同时查看后端日志和任务状态；若 submit=200、events=200 且任务有 `task_end`，则链路正常。

## 4. 容器化过程中的常见坑

### 4.1 `localhost` 的含义改变

容器内的 `localhost` 指当前容器，不是宿主机，也不是另一个服务。容器之间必须使用服务名：

```text
mysql:3306
redis:6379
qdrant:6333
sky-agent:8000
sky-embedding:8001
```

### 4.2 宿主机端口和容器端口不是一回事

例如 `13306:3306` 表示宿主机访问 13306，容器网络访问仍是 3306。不要把宿主机映射端口写进容器内部连接配置。

### 4.3 `depends_on` 不代表应用已就绪

只能依赖健康检查；Embedding 还必须给模型加载留出时间，Agent 也应自身重试。

### 4.4 环境变量不会自动进入已运行容器

修改 `.env` 或 Windows 系统变量后，使用 `up -d` 可能不会重建容器。配置变化时执行：

```powershell
docker compose up -d --force-recreate sky-agent sky-server
```

### 4.5 非 root 用户和卷权限

镜像内创建的目录权限可能被挂载卷遮蔽。首次挂载后要实际测试写入权限，不能只检查 Dockerfile。

### 4.6 大模型不应打入应用镜像

模型会导致镜像巨大、构建缓慢、升级困难。使用固定 revision、校验值和只读模型卷。

### 4.7 SQLite 不能用多 worker 伪装扩展

Agent 当前任务状态依赖单进程内存和 SQLite，不能简单增加 Uvicorn worker；扩展前需重新设计状态存储。

### 4.8 `docker compose down -v` 会删除数据

`-v` 会删除命名卷，可能清空 MySQL、Qdrant、Agent 和 Server 数据。日常停止应使用 `docker compose stop` 或不带 `-v` 的 `down`。

### 4.9 索引失败不等于 LLM 失败

先查看文档索引状态和错误信息。文档没有成功索引时，Agent 拒答是正确行为，不应先修改 Prompt 或 API Key。

### 4.10 只看容器 `Up` 不够

必须同时查看健康状态、依赖连通性、任务事件、索引状态和持久化结果。

## 5. 日常运维手册

### 5.1 查看状态

```powershell
docker compose ps
docker stats
docker volume ls
```

### 5.2 查看日志

```powershell
docker compose logs --tail=100 sky-server
docker compose logs --tail=100 sky-agent
docker compose logs --tail=100 sky-embedding
docker compose logs -f sky-agent
```

避免在日志中记录 API Key、JWT、完整 Prompt、员工问题和知识正文。

### 5.3 健康检查

```powershell
Invoke-WebRequest http://localhost:8080/actuator/health/readiness
Invoke-WebRequest http://localhost:8000/health/ready
Invoke-WebRequest http://localhost:8001/health/ready
Invoke-WebRequest http://localhost:6333/healthz
```

Embedding 重启后先等待 `/health/ready` 返回 200，再进行知识索引或 AI 问答。

### 5.4 重启与升级

```powershell
docker compose up -d --build sky-agent sky-server
docker compose up -d --build sky-embedding
docker compose ps
```

升级顺序建议：先构建并替换 Embedding，再替换 Agent，最后替换 Java。升级前备份数据，升级后执行健康检查和一条问答回归。

### 5.5 停止与清理

```powershell
docker compose stop
docker compose down
```

只有明确确认数据已备份且允许清空时才执行：

```powershell
docker compose down -v
```

### 5.6 备份

MySQL：

```powershell
docker compose exec -T mysql sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' > backup.sql
```

Qdrant 和 Agent 数据：

```powershell
docker run --rm -v sky-take-out-qdrant-data:/data -v "${PWD}\backup:/backup" alpine tar czf /backup/qdrant-data.tgz -C /data .
docker run --rm -v sky-take-out-agent-data:/data -v "${PWD}\backup:/backup" alpine tar czf /backup/agent-data.tgz -C /data .
docker run --rm -v sky-take-out-server-data:/data -v "${PWD}\backup:/backup" alpine tar czf /backup/server-data.tgz -C /data .
```

备份文件应存放在受控位置并加密，恢复前停止相关服务。

### 5.7 恢复与演练

1. 停止应用写入。
2. 恢复 MySQL dump。
3. 将 Qdrant、Agent、Server 备份解压回对应命名卷。
4. 启动 Compose。
5. 检查所有 readiness。
6. 查询一条已知知识文档并验证引用。

恢复演练必须定期执行，不能只确认备份文件存在。

### 5.8 磁盘与资源监控

重点关注：

- BGE-M3 模型占用约 4.27 GB。
- Docker 镜像、构建缓存和日志增长。
- MySQL、Qdrant、Agent 数据卷增长。
- Embedding CPU 和内存峰值。
- Agent 任务积压与失败数。

必要时使用：

```powershell
docker system df
docker builder prune
```

清理前确认不会删除仍需使用的镜像、卷或构建缓存。

## 6. 故障定位决策树

```text
AI 无响应
  |
  +-- sky-server 不 healthy？ -> 查 Java、MySQL、Redis、Flyway
  |
  +-- sky-agent 不 healthy？  -> 查 LLM 配置、Qdrant、Embedding readiness
  |
  +-- sky-embedding 不 healthy？ -> 查模型路径、权限、内存、加载日志
  |
  +-- submit 返回 4xx？ -> 查 JSON body、Content-Type、请求契约
  |
  +-- submit 成功但拒答？ -> 查知识库文档状态、授权版本和是否有证据
  |
  +-- SSE 已结束？ -> 查 task_end 事件和任务最终状态
```

## 7. 当前系统边界

- Agent 保持单实例、单 worker 约束。
- 当前 RAG 只能回答已授权且成功索引的知识内容。
- 实时订单、菜品、库存查询需要后续只读业务工具模块。
- Compose 是单机编排，不等于高可用。
- 外部 LLM 的限流、余额、模型权限和网络质量仍需单独监控。
